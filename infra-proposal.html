1. 前提条件と想定規模

初年度の運用規模想定

項目想定値根拠 / 補足
採用自治体数10 〜 20近隣自治体との直接商談ベース
プレイヤー数(累計DL)数百1自治体あたり数十名を想定
公開譜面数100 〜 300 / 年自治体あたり 5 〜 15 譜面を想定
公開リクエスト頻度10 〜 30 / 月制作は集中的に行われる想定(祭りシーズン前)
DL リクエスト頻度500 〜 2,000 / 月プレイヤー × 平均 2-3 譜面 × 月内複数DL(再インストール等)

ストレージ総量~10 MB(初年度)300 譜面 × 20 KB でも 6 MB 程度
結論のプレビュー: この規模なら GCP の主要サービスはすべて 無料枠内 に収まる。 実質的な運用コストは 月額 ¥0 〜 ¥100 程度(GCP 部分のみ)。

2. 構成方針

  • GCP 中心 — ユーザーが業務で慣れているため学習コスト低減
  • フリーティア内収まりを最優先 — 初年度規模なら実質無料で運用可
  • サーバーレスを徹底 — 常時稼働型サーバー(GCE, Cloud SQL 等)は使わない、リクエスト単価のみ
  • カスタムドメイン + HTTPS Load Balancer は MVP では見送り — 月 $18+ かかるため過剰。GCS/Cloud Run のデフォルトドメイン(storage.googleapis.com, *.run.app)を利用
  • CDN は導入しない — 想定 DL 頻度なら Cloud Storage 直配信で十分
  • 可用性より価格 — マルチリージョン化はしない(asia-northeast1 Tokyo のみ)

3. 構成図

クライアント(iOS) GCP サービス 外部サービス

データフロー概要

  • 譜面DL (プレイヤー): iOS アプリ → GET storage.googleapis.com/[bucket]/{id}.json → Cloud Storage 直配信
  • 譜面公開 (制作者): iOS アプリ → POST *.run.app/publish → Cloud Run → App Store API で JWS 検証 → Firestore で重複確認 → Cloud Storage 書き込み
  • デプロイ: GitHub push → GitHub Actions(build → push → deploy) → Artifact Registry → Cloud Run 更新

4. コンポーネント詳細と選定理由

Cloud Storage

譜面 JSON の配信・保管

選定理由: HTTPS 標準搭載、公開バケットで匿名 GET 可、egress 単価が安く、無料枠 5GB。カスタムドメイン不要なら実質永久無料。

設定: リージョン Standard asia-northeast1、Uniform bucket-level access、allUsers → Storage Object Viewer、ListObjects 権限は付与しない。

Cloud Run

/publish, /check-id の公開API

選定理由: サーバーレスで常時稼働コストゼロ、リクエスト単価のみ、コンテナ形式で柔軟。無料枠が広く(月200万リクエスト)、本規模では実質無料。

設定: リージョン asia-northeast1、min instances = 0(スケール to zero)、認証 = 公開(コード内で IAP 検証)。

Firestore (Native mode)

IAP トランザクション台帳 / 公開ID台帳

選定理由: サーバーレス DB。書き込み頻度が低く、無料枠(20K read/write per day)で余裕。トランザクショナルな重複防止が必要な用途に最適。

コレクション: transactions(使用済み IAP transaction_id)、charts(公開済み chart_id + メタ)。

Secret Manager

Apple 認証情報の秘匿保管

選定理由: App Store Server API 用の秘密鍵/Issuer ID/Bundle ID/App Store shared secret を安全に保管。Cloud Run から IAM 経由でアクセス。

コスト: 秘密数 6 まで無料、アクセス数 10K/月まで無料 → 本規模では ¥0。

Artifact Registry

Cloud Run 用コンテナイメージの格納

選定理由: Cloud Run とリージョン内で密結合し、イメージ pull が高速。GitHub Actions からも gcloud auth で push 可能。無料枠 0.5GB。

備考: イメージサイズを Alpine ベース等で 200MB 以内に抑えれば無料枠内。

GitHub Actions(外部)

CI/CD(build → push → deploy)

選定理由: ユーザーが普段 GitHub Actions を利用しており学習コスト最小。Workload Identity Federation で GCP 認証を鍵レス化できる。無料枠 2,000分/月(Private リポジトリ)で本規模には十分。

フロー: GitHub push → Actions で Docker build → Artifact Registry へ push → gcloud run deploy で Cloud Run 更新。Cloud Build は使用しない。

Cloud Logging

全サービスのログ集約

選定理由: Cloud Run / Cloud Storage / Firestore すべて自動でログが集まる。無料枠 50GB/月 → 本規模では ¥0。

用途: 障害調査、IAP 検証失敗の追跡、DL統計。

Cloud Monitoring

メトリクス・アラート

選定理由: GCP 標準、Cloud Logging 由来のメトリクスが自動で使える。基本無料。

用途: Cloud Run のエラー率アラート、Firestore の読み書き回数モニタ。

6. 検討した代替案

候補採用可否理由
Cloud SQL(PostgreSQL/MySQL)不採用最小構成でも月 $10〜、常時稼働コスト発生。書き込み頻度極低の本用途に過剰
App Engine (Standard)不採用Cloud Run とほぼ同機能だがコンテナ運用の柔軟性・スケール to zero の使いやすさで Cloud Run が上
Cloud Functions不採用関数単位で軽量だが、App Store SDK 依存関係の管理でコンテナベースの方が扱いやすい
Compute Engine (GCE)不採用常時稼働コスト発生。サーバーレスの利点を捨てる理由がない
Firebase Authentication不採用設計上アカウント概念なしのため不要
Firebase Hosting不採用静的サイト用途、譜面配信は Cloud Storage で十分
Cloud CDN初年度は不採用本規模ではキャッシュヒットで得られる帯域節約より、LB 費用($18+/月)が高い。DL 10万/月超えたら再検討
HTTPS Load Balancer + カスタムドメイン初年度は不採用月 $18〜。デフォルトドメイン(*.run.app, storage.googleapis.com)で機能上問題なし。ブランディング上必要になったら追加
Cloudflare (DNS/Proxy)要検討(将来)無料でカスタムドメインが実現できるが、GCP 集約したいユーザー方針に反する。MVP 期は導入見送り
Redis / Memorystore不採用キャッシュ需要なし、常時稼働コスト発生
Cloud Tasks / Pub/Sub不採用非同期処理が発生しないため不要
Cloud Build(CI/CD)不採用ユーザーが普段 GitHub Actions を利用しているため、CI/CD は Actions に一本化。GCP 側の複雑度を減らす

8. リスクと注意点

技術リスク

  • Cloud Run コールドスタート: min instances = 0 のため、初回リクエストで数秒遅延の可能性。公開頻度が低い本用途では許容範囲だが、UX 上気になれば min instances = 1 に(月数百円 追加)
  • App Store Server API のレート制限: Apple は具体的な数値を非公開。per-hour で HTTP 429 + RateLimitExceededError を返し、Retry-After ヘッダで次回可能時刻を通知する仕様。本プロジェクトの想定頻度(月 10-30 公開)なら余裕は膨大で実質影響なし。
    さらに重要: IAP の JWS(署名付きトランザクション)は Apple 公式ライブラリ(AppStoreServerLibrary)で完全オフライン検証が可能。本プロジェクトは Consumable のみで購読状態の照会も不要なため、App Store Server API を1回も呼ばずに公開処理を完結できる設計を採る予定 → レート制限のリスクは実質ゼロ
  • デフォルトドメインのブランド性: *.run.app をアプリ内で見せるとやや素朴。ただしユーザー(iOS アプリ)にとってはコード内定数なので表面には出ない

コストリスク

必須実装項目(実装時に必ず対応): 以下の2項目は個別ドキュメントに具体的な実装チェックリストがある。 実装完了時にチェックリスト全項目を確認し、未完了項目がある場合は本番リリースしないこと。 参照: dev_documents/implementation_notes/cost_protection.md
  • ログ量の暴走【必須実装】: エラー時のスタックトレースや HTTP 200 の詳細ログで無料枠 50GB/月 を圧迫する可能性。Log Router 除外設定、構造化ログ、保持期間14日、Cloud Monitoring アラートを実装
  • Cloud Storage の悪意ある大量DL【必須実装】: 公開バケットのため理論上可能。GCP 予算アラート(¥500/¥1,000/¥3,000)、req 頻度アラート(1時間 1K/10K)、クライアント側キャッシュ、緊急バケット公開停止 Runbook を実装

運用リスク

  • 秘密鍵の管理: Apple の p8 秘密鍵はローテーション不能に近いため、Secret Manager での厳格な IAM 管理必須
  • Firestore データの喪失: 定期エクスポート(週次)を Cloud Scheduler + Cloud Functions で自動化推奨(数百円/月)
  • 取り下げ運用の準備: 譜面取り下げ機能はまだ実装しない前提だが、緊急時のために手動で GCS から削除する運用手順書を用意
