経路ごとのフロー

プレイ経路(赤)

  1. タイトル/メニュー → 「プレイ」タップ
  2. 保存済み譜面一覧 → 譜面を選択
  3. プレイ画面 → ノーツをタップ、演奏
  4. リザルト画面 → スコア表示
  5. 「一覧に戻る」で保存済み譜面一覧へ(または「もう一度」でプレイに再突入)

制作経路(青)

  1. タイトル/メニュー → 「録音」タップ
  2. 録音画面 → 太鼓を叩いて打点を記録
  3. 録音停止 → 譜面編集画面
  4. 編集画面で以下を選択可:
    • 試遊: プレイ画面で自作譜面をローカル再生 → 編集画面に戻る(無料)
    • 保存: ローカル保存 → 保存済み譜面一覧へ(無料)
    • 公開: 公開画面へ(次項)
  5. 公開画面 → 公開ID入力 → /check-id 事前確認 → IAP決済 → /publish アップロード → 発行ID表示 → 保存済み譜面一覧へ

譜面追加経路(緑)

  1. タイトル/メニュー(または保存済み譜面一覧のヘッダ)→ 「譜面をIDで入手」
  2. 譜面検索/DL画面 → ID入力 → ダウンロード
  3. GET https://storage.googleapis.com/ohayashi-charts-{env}/{id}.json → 200なら端末ローカルに保存
  4. 保存済み譜面一覧に追加(新規譜面がハイライトされると尚良い)

設計上の要点
ハブ = 保存済み譜面一覧(02)。ほぼすべての経路がここに帰着する。プレイ経路も、制作経路も、譜面追加経路も、最終的に一覧に新しい状態が反映されて戻ってくる構造。
課金ポイントは 08(公開)のみ。それ以外の画面はすべて無料でアクセス可能。制作者は録音→編集→試遊を無料で繰り返し、最後に公開だけで課金が発生する。

依存関係

データフロー

  • ローカル譜面 JSON: 02 / 04 / 05 / 07 が読み書き、03 / 08 が書き込む
  • GCS 公開バケット: 03 が GET、08 が(バックエンド経由で)PUT
  • Firestore 台帳: 08 が(バックエンド経由で)書き込み、iOS 側は直接触らない
  • StoreKit 2: 08 のみが利用

画面間の主要依存

  • 04(プレイ)は 02(一覧)/ 07(編集の試遊)/ 05(リトライ)の複数元から呼ばれる → 起動元の情報を保持し、終了時に正しく戻す必要あり
  • 07(編集)→ 04(試遊)は「戻る先」が特殊(通常のプレイは 05 へ、試遊は 07 へ戻す)
  • 08(公開)は 07(編集)からのみ到達可能 → 公開への導線は制作フローに閉じている

MVP スコープと将来対応

MVP に含む

  • 01〜08 の全画面
  • ID入力による譜面追加 (03)
  • 録音・編集・保存(無料) (06 / 07)
  • 公開課金(IAP) (08)

MVP では持たない

  • QR コード(公開ID告知用 / DL用)— §8 未決事項
  • AirDrop / Files アプリ経由の譜面共有 — 将来のアップデート予定
  • 譜面のノーツ個別編集 UI(位置の微修正)— 削除のみ or 未実装
  • 譜面の更新公開(再アップロードによる修正)— 実装しない方針
  • アカウント / 認証 — 仕様上不要
  • スコア共有・ランキング — 仕様上不要
