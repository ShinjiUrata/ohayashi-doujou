## 1. Guideline 3.1.1(IAP の必須性)

**Guideline 要旨**: デジタルコンテンツ・機能の販売は Apple の IAP を経由すること。

**本アプリでの該当リスク**:
- 譜面配布に **IAP 以外の動線**があると見なされるリスク
- 特に **AirDrop 対応時**(将来アップデート):
  - 「有料公開せずに AirDrop で無料配布できる」= IAP 回避と誤解される可能性
  - 現状の設計方針は「AirDrop はローカルコピーの延長、譜面公開(サーバー配布)とは別」ではあるが、審査官への説明が必要

**対策**:
- MVP では AirDrop 実装しない(既定)
- AirDrop 追加時の Review Notes に「AirDrop はローカル譜面のコピーであり、譜面公開機能とは異なるスコープ」と明記
- Bundle 内の効果音・素材データは IAP 非依存(問題なし)

---

## 2. Guideline 3.1.3(Consumable の適切な使用)

**Guideline 要旨**: Consumable は「1回使うと消費される」性質のもの。同じ機能への再アクセス目的で Consumable を使うのは不適切。

**本アプリでの該当性**:
- 「譜面公開 1 曲分」は明確に **1 回性の役務**(同じ譜面を再公開しても同じ結果にならない、別 ID なら別譜面)
- Consumable として適切

**対策**:
- Review Notes に説明:
  - 「1 プロダクト = 1 曲分の公開」
  - 「一度使うと同じ公開行為は再現できない(取り下げ→再公開もできない)」
  - 「複数曲公開したい場合は複数回購入する」
- **サブスクリプション / Non-Consumable と混同されないよう明確に説明**

---

## 3. Guideline 1.3(Kids Category)

**Guideline 要旨**: 子供向け(4歳以下 / 5-8歳 / 9-11歳)カテゴリは追加要件あり(第三者広告・行動追跡・課金の親承認 等)。

**本アプリでの選択**:
- **Kids Category は選ばない** — 通常カテゴリ「Games > Music」で提出
- 実際の対象年齢は「子供が触ることも想定」だが、公式ターゲットは「一般利用者」

**理由**:
- Kids Category は審査が厳しく、追加の親承認 UI や独自の COPPA 対応が必要
- 課金機能があるアプリは Kids Category での認可がおりにくい
- 通常カテゴリで「子供が触っても安全な設計」を目指す方が現実的

**対策**:
- カテゴリ: **Games > Music**(Primary)、**Education**(Secondary)を検討
- App Store の年齢制限は「4+」を選択(暴力・不適切内容なし)

---

## 4. Guideline 5.1.1(Privacy)

**Guideline 要旨**: プライバシーポリシーが必須、収集情報の明示、第三者提供の説明。

**本アプリでの対応**:
- プライバシーポリシー URL 必須
- App Privacy 質問への回答:
  - Data Collection: **なし**(基本、通信ログは 14 日保持のみ)
  - トラッキング: **なし**
  - 第三者提供: Apple(決済)、Google(GCP インフラ)
- 「Data Not Collected」を選択できる分野が多いはず

---

## 5. Guideline 4.2(Minimum Functionality)

**Guideline 要旨**: 機能が薄いアプリはリジェクトされる。単一機能で複数アプリを作るのも不可。

**本アプリでの対応**:
- 機能: プレイ / 録音 / 編集 / 公開 / DL の 5 機能
- 譜面数は初期少なくても、機能自体は多層 → OK
- Review Notes で「祭り会場の実運用シナリオ」を説明

---

## 6. Guideline 4.3(Spam)

**Guideline 要旨**: 類似アプリの大量投稿禁止。既存アプリのクローンも NG。

**本アプリでの該当性**:
- 太鼓の達人風だが「お囃子学習」という明確な用途差別化
- 同社の別アプリ(`spanglow`)と機能が完全に別 → 問題なし

---

## 7. IAP の Display Name / Description のローカライズ

**問題**: ローカライズが不十分だと、日本以外の Review 官(米国など)が誤解する可能性。

**対策**:
- MVP は日本のみ販売 → 日本語のみでも技術上 OK
- ただし審査官は英語で見ることも → 英語 Localization もサブとして用意することを推奨
  - Display Name (EN): "Publish a Chart"
  - Description (EN): "Publish one custom rhythm chart to the server so other players can download it."

---

## 8. Review 提出時の必須準備物

**チェックリスト**:
- [ ] Sandbox 用テスト IAP アカウント(App Store Connect で作成)
- [ ] Review Notes:
  - アプリの想定利用シーン(祭り会場、子供が順番に触る)
  - IAP のテスト手順(録音 → 編集 → 公開 → Sandbox 決済 → 発行 ID 確認)
  - **サンプル譜面 ID を提示**(例: `sample-2026-review`)— Review 官が譜面 DL を試すため
  - Consumable 性質の説明
- [ ] スクリーンショット(6.9"/6.5"/5.5" の全サイズ)
- [ ] App プレビュー動画(推奨、なくても可)
- [ ] Rating Questionnaire 回答(4+ 対象、暴力・恐怖・アルコール・ギャンブル等すべて None)
- [ ] Export Compliance(暗号化: HTTPS のみなら Exempt / Standard)

---

## 9. サンプル譜面の事前公開

**問題**: Review 官が譜面 DL を試そうとしても、初回リリース時はサーバーに譜面が 1 つもない状態。

**対策**:
- リリース申請前に **開発者アカウントで数曲を先行公開**
- MVP では自社内での公開なので実質無料
- Review Notes にサンプル ID を書く(例: `sample-2026-review`, `demo-shishimai`)

---

## 10. リジェクト時の対応方針

**問題**: 初回リジェクトは高確率で発生する。対応の姿勢で審査時間が延びる。

**対策**:
- **真摯に応答**、無視・強弁は絶対に避ける
- Apple の指摘を丁寧に読み、事実誤認があれば根拠を示して反論
- 「私たちの理解では〜」と丁寧に説明
- 判断が別れそうなポイントは事前に **App Review Board** に問い合わせ可能
- 数日〜1週間で再審査が返る

---

## 11. Guideline 3.1.5(Cryptocurrencies)、5.2(Intellectual Property)

**該当性**:
- 暗号通貨: 無関係(該当なし)
- 知的財産: **お囃子の楽曲は伝統的なものが多いが、特定のアレンジは著作権あり**
- 譜面公開者が既存の商用楽曲の譜面を勝手に公開するリスク

**対策**:
- 利用規約で「公開者が著作権侵害の責任を負う」旨を明記
- Apple には「公開者が自身の責任で公開する」設計として説明
- 権利者からの申し立てがあれば個別に取り下げる運用(Runbook)

---

## 12. アイコン / スクリーンショットの審査

**問題**: 意匠が「他社商標と類似」と見なされるリスク(太鼓の達人 → バンダイナムコ)。

**対策**:
- 意匠デザインを独自に(太鼓 + 「囃」文字 + 和柄 = 独自性が高い)
- 太鼓の達人らしい配色(青ドン・赤カッ 等)を模倣しない
- 本アプリは **赤ドン・青カッ**(逆)なので差別化されている
- 「和太鼓」自体は伝統文化なので意匠使用に問題なし

---

## 13. サブスクリプション見なされ対策

**問題**: 「継続的にサーバーが譜面を配信し続けている」という側面がサブスクと解釈される可能性。

**対策**:
- Review Notes と利用規約で明確に:
  - 「¥1,000 は 1 曲の公開行為に対する対価」
  - 「配信は publish の副次的結果」
  - 「継続的なサービス提供ではない」

---

## 14. リリース戦略

**問題**: 審査通過後、即時リリースだとサーバー障害・アプリ側の問題を即座に世に出してしまう。

**対策**:
- **Manual Release** を選択(審査通過後、自分でリリースボタンを押すまで公開されない)
- リリース前にサーバー最終確認・監視強化
- リリース直後 24 時間はコスト・エラー率を頻繁にチェック

---

## 15. アップデート審査の注意

**将来アップデート時**:
- **AirDrop 追加時**: Review Notes に「IAP 回避ではない」説明を必ず入れる(§1 参照)
- **QR スキャン追加時**: カメラ権限の目的説明を Info.plist の `NSCameraUsageDescription` に明記
- **BGM 対応時**: 著作権のある楽曲を含まない旨を明示、フリー素材ならライセンス表記
