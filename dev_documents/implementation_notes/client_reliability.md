# オフライン / 信頼性 — 気をつけること

**位置付け**: 通信失敗・データ整合性・IAP 決済とアップロードの分離に関わる注意点。祭り会場での電波不安定下でも壊れないアプリ設計。

## 1. 譜面 DL 中の通信切断

**問題**: DL 途中でネットワークが切れると、部分書き込みされた壊れた JSON がローカルに残る。

**対策**:
- **一時ファイル → 完全に書けたらリネーム**方式:
  1. `charts/{id}.json.tmp` に書き込む
  2. 完全書き込み + JSON パース検証成功時のみ、`charts/{id}.json` にリネーム
  3. 失敗時は `.tmp` を削除
- `URLSession.downloadTask` を使うと自動的に一時ファイル方式になる
- リトライは自動化しない(ユーザーが明示的に再試行)

---

## 2. 譜面公開フローでの通信切断(最重要)

**問題**: IAP 決済成功後、`/publish` 呼び出しで通信が切れると、「¥1,000 課金されたが譜面はサーバーにない」状態になる。

**対策**:
- **`Transaction.finish()` は publish 成功レスポンス受信後にのみ呼ぶ**
- publish 失敗時は finish しない → StoreKit が「未完了トランザクション」として保持
- アプリ起動時に `Transaction.updates` を購読、未 finish のトランザクションを検知
- ローカルに残っているドラフト譜面と紐付けて再送提案 UI を出す
  - 「未公開のトランザクションが 1 件あります。再度公開しますか?」

---

## 3. 未確定 publish の再送設計

**問題**: 未 finish トランザクションと、対応する譜面 JSON が結びつかないと再送できない。

**対策**:
- ドラフト譜面(公開前)を保存する際、`pending_transaction_id` を JSON に含める(あるいは別のマッピングファイル)
- Transaction.updates で受け取った未 finish の `transaction_id` から譜面ドラフトを特定
- 発見できなかった場合(端末を替えた等):ユーザーサポートで対応

---

## 4. サーバー側 publish 失敗時の冪等性

**問題**: iOS 側が同じ JWS で再送しても、サーバー側が冪等でないと Firestore に二重書き込みされたり GCS に古い状態のまま残ったりする。

**対策**:
- サーバー側の `/publish` は同じ `transaction_id` で再送されたら、以前の処理結果を返す(冪等)
- 完了状態を Firestore の `transactions/{transaction_id}` で判定
- 完了済みなら「その時の chart_id」をレスポンス
- 途中失敗状態(Firestore は成功、GCS は失敗)のリカバリは Runbook 化

---

## 5. Chart JSON の後方互換性

**問題**: 将来的にフィールドを追加した時、古いアプリで JSON パースが失敗する。

**対策**:
- 新フィールドは全て Optional で追加
- iOS 側の `JSONDecoder` は未知のキーを無視する(デフォルト挙動)
- スキーマバージョン `schema_version` フィールドを最初から入れておく余地(現状は入っていないが、必要時に追加)
- 互換性のない変更(フィールド削除・型変更)は絶対に避ける

---

## 6. ローカル ID とサーバー ID の混同

**問題**: 録音直後は「ローカル ID(UUID)」、公開後は「サーバー chart_id」と、同じ譜面に 2 種類の ID が存在する。混同するとファイル重複・上書き事故になる。

**対策**:
- 保存ファイル名の規約を明確に:
  - ドラフト: `charts/draft-{UUID}.json`
  - 公開済み: `charts/{chart_id}.json`(接頭辞なし)
- 公開成功時にドラフトファイルをリネーム or 削除して新ファイル作成
- ライブラリ画面で両者を区別表示(「ドラフト」バッジ vs「公開済み」バッジ)

---

## 7. ローカル DL 済み譜面 vs 公開済み譜面

**問題**: 自分が公開した譜面と、他人の譜面を DL したものが同じ `charts/{chart_id}.json` で保存される。区別が付かないと管理が混乱する。

**対策**:
- Firestore の `charts.{id}` にメタデータを持つが、ローカルでは全て同じ扱いでよい
- ただし「自分が公開した」フラグをローカルに持っておく(削除しないほうがよい譜面を明示)
- 削除確認ダイアログで「これはあなたが公開した譜面です」を表示

---

## 8. ドラフト譜面の寿命

**問題**: 編集画面を離れる時に保存しないとドラフトが消える → ユーザーが録音を無駄にする。

**対策**:
- 編集画面 → タイトルに戻る時、保存/破棄の確認ダイアログ
- アプリ強制終了(スワイプアップ、クラッシュ)時のドラフト保護:
  - 録音停止時に自動でドラフトを保存
  - 編集画面ではリアルタイムに `Application Support/drafts/{UUID}.json` に反映

---

## 9. StoreKit のオフライン購入

**問題**: 一部の状況では購入が「オフライン扱い」で進み、ネットワーク復帰後にトランザクションが返る。

**対策**:
- `Transaction.updates` を必ず購読(起動時 + アプリ全体で継続)
- ネットワーク復帰後の Transaction 到着時、自動的に publish を試みる or ユーザーに通知
- 「決済は完了しているが公開処理中」の状態表示

---

## 10. Cloud Run の cold start

**問題**: Min Instances = 0 の設定だと、初回リクエストで数秒〜10秒の遅延が起きる。

**対策**:
- iOS 側でローディング表示を丁寧に(「サーバー起動中」等の説明を含める)
- タイムアウトは 30 秒に設定(通常 5 秒で十分だが cold start 対応)
- `/check-id` を先に叩いて warm up する副次効果あり
- 頻繁アクセスが増えたら Min Instances = 1 に切り替え

---

## 11. サーバー側の 5xx エラー

**問題**: 5xx を受けたときに finish() してしまうと、ユーザーが再試行できない。

**対策**:
- 5xx を受けたら `Transaction.finish()` を **絶対に呼ばない**
- ユーザーに「時間を置いて再試行してください」を表示
- ローカルにドラフトを保持し、後で再送

---

## 12. 端末時刻のずれによる created_at のずれ

**問題**: 端末時計が大きくずれていると、譜面の `created_at` が未来 or 過去になる。

**対策**:
- 譜面 JSON の `created_at` は iOS 側で `Date()` を使うが、参考値として扱う
- 譜面公開時のサーバー側で **バックエンドが `created_at` を上書き**(GCP のサーバー時刻を信用)
- 端末側のズレはユーザーには特に説明不要

---

## 13. 効果音ファイルの検証

**問題**: Bundle 内 WAV が何らかの理由で読み込めないと、プレイ画面で無音になる。

**対策**:
- アプリ起動時に必要な効果音ファイルの存在確認
- 欠落時:
  - 開発中: `fatalError`
  - 本番: 「アプリを再インストールしてください」の穏やかな表示
- ダウンロードコンテンツではなく Bundle 同梱なので、通常は起きないが Fallback として

---

## 14. パース失敗時のファイル退避

**問題**: JSON 破損時に安易に削除するとユーザーサポート時にログが取れない。

**対策**:
- 破損検知時: `Application Support/quarantine/{timestamp}-{id}.json` に退避
- 退避後はローカルライブラリから消える
- ユーザーサポート時にファイルを取り出せる(App Sharing 経由か、開発者と個別対応)

---

## 15. iOS のバックグラウンド遷移とアプリ状態

**問題**: プレイ中にホームボタン(ジェスチャ)でバックグラウンドに行った時、譜面プレイの状態が保存されないと再開時に混乱する。

**対策**:
- バックグラウンド遷移時にプレイを一時停止
- 復帰時は「一時停止中」画面を表示、明示的に再開ボタンをタップ
- 一定時間(5 分)経過後の復帰は、プレイを破棄してタイトルに戻す

---

## 16. アプリバージョンとサーバー側の互換性

**問題**: 古いバージョンのアプリが新しいサーバー API を叩く、あるいはその逆。

**対策**:
- API バージョニング(パスに `/v1/` を含める)を最初から採用
- MVP は `v1` 固定でよい
- 将来 `v2` を出す時に古い `v1` は当面残す

---

## 17. 通信ライブラリの選択

**問題**: サードパーティ HTTP ライブラリ(Alamofire 等)は便利だが、依存が増えて Xcode プロジェクトが複雑化する。

**対策**:
- MVP は Foundation の `URLSession`(async/await)で十分
- サードパーティ依存を追加するのは、URLSession で明確な限界が見えた時のみ

---

## 18. GCS のキャッシュヒット

**問題**: 同じ譜面を何度も DL するとサーバーコストが跳ねる(`cost_protection.md` §2C)。

**対策**:
- iOS 側で「ID 検索 → ローカルヒット判定 → 存在すればスキップ」を最優先ロジックに
- サーバーへは「DL 押下時に本当に必要な時だけ」リクエスト
- HTTP キャッシュヘッダを尊重(GCS 側で Cache-Control を返す)

---

- [ ] 譜面 DL は一時ファイル方式(`.tmp` → リネーム)

- [ ] ドラフト譜面に `pending_transaction_id` を保持
- [ ] サーバー側 `/publish` の冪等性
- [ ] Chart JSON の後方互換性(Optional 新フィールド)
- [ ] ローカル ID とサーバー ID の混同防止(接頭辞 `draft-`)
- [ ] 自分が公開した譜面のフラグ管理
- [ ] ドラフト自動保存(録音停止時 + 編集画面で継続)
- [ ] Cloud Run cold start 対応のローディング表示
- [ ] 5xx エラー時は finish() しない
- [ ] created_at はサーバー側で上書き
- [ ] Bundle 効果音の起動時検証
- [ ] 破損 JSON はファイル退避
- [ ] バックグラウンド遷移時の一時停止
- [ ] API バージョニング(/v1/)採用
- [ ] URLSession + async/await(サードパーティなし)
